# Database

MongoDB through Mongoose 8, one connection (`db/DBConnection.js`). The connection string comes only from the environment (`MONGO_URL` in production, `MONGO_URL_LOCAL` otherwise). No migration runs by itself: every change to stored data is a script in `scripts/migrations/` that does a dry run by default.

## Collections and how they relate

Generated from the `ref:` fields in `models/` (arrows read "points to"). A school owns almost everything; the `school` link is what keeps schools apart.

| Model | Points to | Notes |
|---|---|---|
| School | | `code` is unique and public (login page lookup). |
| User | School | Staff and platform accounts. `role`: administrator, teacher, … and `platform_admin` (no school). `username` and `email` unique across schools. `mustChangePassword` marks default or admin-set passwords. |
| StudentAuth | School | A student's login. Same `_id` as the Student. `indexnumber` unique across schools. `mustChangePassword` as above. |
| Student | School, Level, User (createdBy) | `indexnumber` unique across schools. Students are deactivated (`active: false`), never deleted. `level` is the current class. |
| Session | School, User | Academic year. |
| Term | School, Session | Exactly one `status: "current"` per school (enforced by the code; see migration 001). Holds `exams.scorePreference` (e.g. "40/60"), dates, headmaster. |
| Level | School, Session, Term, Department, Grade, Fee, Subject, Student, User (teacher) | A class **for one term**: a student appears in a new Level document each term, so Level history must not be edited retroactively. |
| Subject | Session, Term | Scoped to a school through its term. |
| Course | School, Session, Term, Level, Subject, User (teacher) | Which teacher teaches which subject in which class. |
| Grade | School, Session, Term | Grading scale (`ratings`). |
| Department, House | School, Session, User | |
| Examination | School\*, Session, Term, Level, Student, User | One per student per term. `scores[]` entries: `_id` (subject id), `subject`, `classScore`, `examsScore`, `totalScore` (computed by the server), `grade`, `remarks`. `comments.autoGenerated` marks machine-written remarks. |
| Fee | School, Session, Term, Level, User | Fee structure for a class in a term: `amount[]` items. |
| CurrentFee | School\*, Session, Term, Level, Student, Fee, User | A student's payments for a term: `payment[]` entries (`paid`, `outstanding`, `createdAt`, `issuerID`, `issuerName`, `id` receipt). Records with payments are never deleted. |
| Attendance | Session, Term, Level, User | One register per class per day (`date` is midnight UTC). |
| Parent | School, Student | Deactivated, not deleted. |
| Message, Announcement, Event, Holiday, Note, Notification | School, Session, Term, User | `Notification` also points to StudentAuth. |
| ActivityLog | User | Defined but not written by the application yet. |
| CurrentLevel, CurrentLevelDetail, OverAllScore | | Legacy models kept for compatibility; nothing in the current routes depends on them (verify before removing). |

\* `school` was added to `Examination` and `CurrentFee` in Stage 8. Older records do not have it and are scoped through their term. A backfill is a separate, optional migration (see below).

## Money and scores

- Amounts and scores are stored as plain numbers (cedis, not minor units). Every sum is added in whole pesewas by `common/money.js` and `common/scores.js` so totals never show floating point noise. Moving storage to integer minor units would need a data migration and was deliberately not done.
- A payment is valid when `paid` is above 0 with at most 2 decimals. Existing stored payments are not changed; run the data audit (`scripts/data-audit.js`) to find ones that break these rules.

## Indexes

- Declared in the models. Mongoose creates missing indexes when the app starts (`autoIndex`), which is a write: do not point the audit script or a one-off script at production through the models.
- A test (`tests/cleanup.test.js`) fails if any model declares the same index twice.
- **Not enforced by the database yet** (the application enforces them, but two simultaneous requests could still break them): one current term per school (migration 001 adds the index), one register per class and day, one exam record and one fee record per student per term. These unique indexes will fail to build if duplicates already exist, which is why the data audit comes first.

## Migrations and audits (all in `scripts/`)

| Script | Writes? | Purpose |
|---|---|---|
| `data-audit.js` | never (bare driver, read-only) | Report of duplicates, missing or dangling school links, orphans, cross-school references, payment and score anomalies, index inventory. Run with a read-only database user. |
| `migrations/001-one-current-term.js` | only with `--apply` | Checks every school has at most one current term, then creates the partial unique index `one_current_term_per_school`. Rollback: `db.terms.dropIndex("one_current_term_per_school")`. |
| `create-platform-admin.js` | yes | Creates the first platform administrator (credentials from environment variables, never committed). |

Rules for any future migration: dry run by default, `--apply` to write, idempotent, prints its own rollback, never deletes data (deactivate or archive instead), and is run against a backup-restored copy first.
